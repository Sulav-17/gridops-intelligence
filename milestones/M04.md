Objective

Create the trusted forecasting evaluation foundation for GridOps Intelligence.

M04 must establish point-in-time-safe feature snapshots, a clear forecast issuance contract, leakage-safe as-of joins, baseline forecasting models, rolling or expanding backtesting, metric persistence, and reproducible evaluation reports.

M04 is not the production-model milestone. It exists to prove that the data, features, validation design, and baseline comparisons are trustworthy before M05 introduces production forecasting and MLOps.

Completion Statement

M04 succeeds when every training and evaluation row is point-in-time safe, baseline forecasts are reproducible, forecast metrics are persisted or reported with lineage, and slice-level evaluation is available for future model comparison.

M04 should leave the repository ready for M05 production forecasting.

Core Forecasting Contract

M04 must define a forecast issuance contract.

The contract should answer:

At what time is the forecast issued?
What target hours are being predicted?
What data is allowed to be used?
What data is forbidden because it would not have existed yet?
How are archived forecasts selected?
How is quality blocking applied?
How is lineage recorded?

Recommended default:

Forecast type: day-ahead hourly Ontario demand forecast
Forecast horizon: next 24 hourly intervals
Forecast issuance time: configurable, default documented
Target: Ontario hourly electricity demand
Canonical time: UTC
Local interpretation: America/Toronto

The exact issuance time should be documented and justified based on available data assumptions.

If the correct operational issuance convention is uncertain, choose a conservative configurable default and document the assumption.

Point-in-Time Safety Rules

Point-in-time safety is mandatory.

For every feature row:

demand lags must use only intervals before the forecast issuance time
rolling features must use only known historical demand
weather observations must not include future observed weather
archived weather forecasts must be selected by issue time
forecast issue time must be less than or equal to the forecast issuance time
actual target demand must never be used as a feature
revised source records must respect current M02/M03 lineage behavior
quality-blocked data must be excluded or clearly marked unusable

No random train/test splitting is allowed.

Use rolling or expanding time-based validation.

Baseline Models

M04 must implement baseline models before production models.

Baseline 1 — Same Hour Yesterday

Predict each target hour using the observed demand from the same local or UTC hour one day earlier.

The chosen convention must be documented.

DST behavior must be handled explicitly.

Baseline 2 — Same Hour Last Week

Predict each target hour using the observed demand from the same hour seven days earlier.

This is a strong electricity-demand baseline and should be included unless unavailable data prevents it.

Baseline 3 — Seasonal Hourly Mean

Predict using a historical mean grouped by calendar and hour features.

The grouping should be simple and documented.

Acceptable examples:

hour of day
month and hour
weekday and hour
season and hour

Avoid complex tuning.

Baseline 4 — Ridge Regression

Train a transparent Ridge regression baseline using selected lag, calendar, and weather features.

Rules:

use time-based training windows
no random split
no future leakage
standardization is allowed inside a pipeline
features must be reproducible
model parameters must be documented
the model should remain interpretable and simple

Quality-Gate Integration

M04 must respect M03 quality outputs.
