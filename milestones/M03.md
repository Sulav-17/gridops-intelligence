Objective

Build the formal data quality and observability layer for GridOps Intelligence.

M03 must prevent malformed, incomplete, duplicated, stale, discontinuous, or incorrectly timestamped source data from contaminating downstream datasets and later model training.

M03 builds on M02 ingestion. It does not replace ingestion. It adds explicit quality contracts, check execution, quality-result persistence, source-health reporting, and blocking behavior for unsafe downstream publication.

Completion Statement

M03 succeeds when defined data-quality failures are detected, classified, persisted, tested, visible through an API or operational report, and capable of blocking unsafe downstream publication.

M03 should leave the repository ready for M04, where trusted point-in-time feature snapshots and baseline backtesting will begin.

Quality Check Categories

M03 should support checks in these categories.

1. Schema Checks

Validate expected columns, types, and required fields for M02 datasets.

Apply to:

IESO hourly demand records
weather observation records
archived weather forecast records
raw snapshot metadata
ingestion run records where useful

Schema checks should catch missing or unexpected required fields.

2. Completeness Checks

Validate whether required records are present for a given dataset and time window.

Examples:

expected hourly IESO demand intervals exist
weather observations exist for expected timestamps
archived weather forecast valid times exist for expected issue windows where fixture assumptions support it

Completeness should be time-window aware.

3. Continuity Checks

Validate that time series records are continuous where required.

Examples:

hourly demand intervals should not have unexplained gaps
weather observations should not have unexplained gaps inside a checked window
forecast valid times should be logically ordered

Continuity checks must respect DST behavior and M01 time rules.

4. Uniqueness Checks

Validate that normalized records do not contain duplicate current facts for the same business key.

Examples:

IESO demand should not have duplicate current records for the same source-native date and hour-ending, or normalized interval key
weather observations should not have duplicate current records for the same station or location and valid timestamp
archived weather forecasts should not have duplicate current records for the same issue time, valid time, location, and variable set

Revision history or superseded records should not be incorrectly flagged as duplicates if the M02 schema distinguishes current and superseded records.

5. Range Checks

Validate reasonable value ranges.

Examples:

demand MW must be non-negative
demand MW must be within a documented plausible range
temperature must be within a documented plausible range
humidity should be between 0 and 100 when present
wind speed should be non-negative
precipitation should be non-negative

Use conservative ranges and document assumptions.

Do not invent claims about official operational limits unless supported by source documentation.

6. Freshness Checks

Validate whether source data is recent enough relative to expected availability.

Examples:

latest IESO demand timestamp is within expected tolerance
latest weather observation timestamp is within expected tolerance
latest archived forecast issue time is within expected tolerance

Freshness thresholds should be configurable and documented.

Tests should use fixed clocks, not the machine’s real current time.

7. Timestamp and DST Checks

Validate timestamp correctness.

Checks should cover:

timezone-aware UTC timestamps
interval start before interval end
IESO interval duration
America/Toronto interpretation where applicable
source-native date preservation
source-native hour-ending preservation
23-hour DST spring-forward day behavior
25-hour DST fall-back day behavior
ambiguous local timestamps
nonexistent local timestamps

Do not weaken M01 time behavior.

8. Source Metadata Checks

Validate raw snapshot and ingestion metadata.

Examples:

raw snapshot has content hash
raw snapshot has retrieval timestamp
raw snapshot has parser version
ingestion run has valid status
failed ingestion run has safe failure detail
source name and source type are present
Blocking Logic

M03 must implement publication-blocking logic.

A simple function or service is enough.

Blocking logic should answer:

Can this dataset and time window be used downstream?

The decision should be based on persisted quality results.

Suggested behavior:

info does not block
warning does not block by default
error blocks the affected dataset or window
critical blocks the dataset or source

The exact behavior must be documented.

Do not build a full alert lifecycle. That belongs to M06.
